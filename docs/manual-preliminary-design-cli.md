# Offline manual preliminary design CLI

`oabm-manual-design` makes the existing local manual-device intake and preliminary-design boundary usable from files. It does not observe a source, register a drawing, verify field placement or clearance, size conductors, establish code compliance, approve engineering, or connect to OfficeAdmin. All placement, source, grouping and design facts remain caller assertions. The design command retains the existing limits of four admitted devices and 512 candidate model entities. Intake preparation can report more than four admitted devices, but the design command will refuse that request; it does not split work into batches. Unresolved rows remain unresolved. Physical line-and-arc routes remain unsupported by this older router.

## Inputs and workflow

Use a canonical model JSON file and an intake JSON object containing exactly `request_id`, `source_sha256`, `base_model_sha256`, `frame_id` and `items`; the object and row shape are defined by `contracts/manual-device-request-v1.schema.json`. The source SHA is a caller assertion. The frame and coordinates must already match the model's right-handed, +Z, metre coordinate system. Do not put source drawings in these inputs.

1. Run `oabm-manual-design model-digest --model MODEL.json` and place its printed fingerprint in the intake object's `base_model_sha256`.
2. Run `oabm-manual-design intake-digest --intake INTAKE_WITHOUT_DIGEST.json`. Add the printed value as `request_sha256` in the intake object, saving that full object as a separate private intake file.
3. Run `oabm-manual-design prepare --model MODEL.json --intake INTAKE.json --output NEW_INTAKE_REPORT.json`. The private report has the candidate model fingerprint and admitted device/port identities needed for the design decision, plus unresolved items and limitations. Review the facts; a digest is correlation, not authentication or evidence of review.
4. Create a separate private decision JSON conforming to `contracts/manual-design-decision-v1.schema.json`. Bind `candidate_model_sha256` and `intake_request_sha256` to the intake report. Supply every admitted device's explicit group and load-port mapping, the existing panel/source, all circuit rules and routing controls, and a caller-selected allowed domain. The CLI does not fill or infer these facts. The selected panel must have no existing port connections, connected routes, circuiting or owned design; this boundary does not append to or replace an existing panel design.
5. Run `oabm-manual-design decision-digest --decision DECISION.json`. Review the decision and copy its printed digest.
6. Run `oabm-manual-design design --model MODEL.json --intake INTAKE.json --decision DECISION.json --decision-sha256 DECISION_DIGEST --output NEW_DESIGN_BUNDLE.json`.

The design bundle is one JSON object with `version`, `designed_model` and `report`. The report includes the exact bindings, newly produced IDs, unresolved items and limitations. The original model and all inputs remain unchanged. To produce a standalone canonical model for other tools, run `oabm-manual-design extract-model --bundle NEW_DESIGN_BUNDLE.json --output NEW_MODEL.json`. It checks the report shape and that the model fingerprint matches the bundle report before writing. Those checks are consistency only: a forged model and report can agree, and the command does not authenticate or verify either. The bundle itself is not a standalone model file. The output is a detached preliminary proposal, not the saved reviewed-electrical workflow or evidence of real-project acceptance. Changing the source assertion, base model, intake, or decision requires recomputing and reviewing the affected bindings.

## File and privacy behavior

Each input must be an existing regular UTF-8 JSON file. Intake and decision files are limited to 1 MiB each; canonical model and design-bundle files are limited to 8 MiB each; symlinks in the final input path component, FIFOs and devices are refused. Parsing rejects duplicate object keys, nonfinite numbers, invalid UTF-8, excessive nesting and excessive token/node counts. The CLI takes bounded snapshots and checks file metadata before and after each read; this is not source authentication and does not defend against a malicious same-user process capable of changing files and metadata concurrently. Use trusted input and parent directories.

`--output` names a **new** file in an existing trusted directory. No input is overwritten, no parent directories are created, and an existing file, directory or dangling symlink at that name is refused. The result is written as a private temporary file with permissions no broader than owner read/write, then linked atomically under the requested name without replacement. Output is capped at 8 MiB and is structurally checked before publication so the CLI will not publish a bundle it cannot read back. An otherwise valid deeply nested model may be refused when wrapping it would exceed the output depth/node limit. The output file and intake report can contain private model facts and source IDs; keep their directory, backups and sharing private. This POSIX workflow requires hard-link support in the selected directory. Unsupported filesystems fail rather than fall back to overwriting. It does not promise crash durability; after an interruption or a reported failure, inspect the chosen path and any owner-only `.oabm-manual-*.tmp` file before retrying. If publication succeeds but temporary-file cleanup fails, the command reports that the output was created and the private temporary file may remain. Intermediate path components and same-user processes are trusted; this is not a general hostile-directory sandbox.

Fingerprint commands print only the digest to standard output. Prepare/design write the selected file and do not print the model or report. Errors are generic and do not deliberately include input values or paths. File limits bound input and output size, not routing runtime or total memory. The design command uses the existing preliminary router and its current per-route safeguards; no cumulative-work guarantee is claimed. No network calls, providers, uploads, production changes or deployment are performed by the CLI.
