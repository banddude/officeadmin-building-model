# Full System BIM Roadmap

**Snapshot:** 2026-10-16, main at ab3c9eb8adf1c20b48540f5eac63e5c94c92cf7b

This roadmap covers all 23 currently open issues and every current or immediately relevant pull request in banddude/officeadmin-building-model. The goal is reusable plans-to-buildable-model software: jobs are independent acceptance cases for the same engine, not one-off takeoffs. One canonical semantic model remains the source of truth for imports, design proposals, routed systems, quantities, drawings and exports.

Every fact must retain its source, transform, provenance class, confidence and unresolved ambiguity. AI may make small structured proposals; deterministic validation owns model changes and engineering calculations. Source-observed, inferred, proposed and user-confirmed objects remain distinguishable. Where the input or rule basis is insufficient, the system reports the gap rather than presenting a guess as a verified result.

No new GitHub issues are created or closed by this roadmap. Work is sequenced by dependencies, not calendar promises. Routine implementation choices should proceed under the gates below; source access, code-basis or scope questions that cannot be resolved from approved evidence remain explicit decision points.

## Read the status labels separately

- **Implemented** means a code path or artifact exists on the checked-out main commit. It does not mean every consumer uses it or that a job passed.
- **Merged** means a pull request is in main. This is a repository state, not a real-plan acceptance result.
- **Validated on real data** means a fresh run on an authorized real job, with no answer-derived input hints, compared against an independent human-reviewed reference. Synthetic tests and a run that uses its expected output as input do not qualify.
- **Integrated/live** means the OfficeAdmin user experience demonstrably consumes the engine output in a released or production flow. The README describes that integration as future work; this snapshot contains no verified live integration claim.

All 23 issues listed below remain open. Main contains substantial partial implementation: the canonical contract and provenance rules; RoomPlan, PDF, and OABM-authored IFC lanes; deterministic routing; quantities and drawings; proposed electrical design; confidence review; scope reports; explicit box, raceway, support and framing objects; revision diffs; and GLB/IFC layer and display options. The existing docs describe these boundaries in [architecture](architecture.md), [model contract](model-contract-v1.md), [responsibility relay](responsibility-relay.md), [PDF convergence](pdf-convergence.md), [routing](routing.md), [quantities](quantities.md), [proposed electrical design](proposed-electrical-design.md), [bounded proposals](bounded-proposals.md), [confidence review](confidence-review.md), [IFC adapter](ifc-adapter.md), and [QA golden fixtures](qa-golden-fixtures.md). These foundations are not a complete, independently accepted plan-set-to-installation package.

At this snapshot, a fresh full-system real-job acceptance on current main has not been evidenced, and no OfficeAdmin production integration has been verified. Older audits and private runs are signals to re-check, not current-main validation. No 90% vision-accuracy claim is made; the benchmark status supplied for this roadmap is one human-confirmed visual case.

## Critical path and delivery waves

### Wave 1: prove raw plan evidence and registration

The current critical path is #42, #224 and #259: raw pages must produce trustworthy architectural regions, scale/registration and recognized devices before downstream design can be trusted. O1 and O3 are active in those areas. Acceptance must use the current main commit, an independent reference and no answer-derived hints. Private real-job files and results stay outside this public repository.

#76 is a hard gate before real panel recognition or any source-observed circuit can ship. Its current interim enclosure-edge guard is not a semantic classifier for walls and other architectural linework. #72 can proceed in parallel on device counts, source-evidence parsing, and architectural-only design proposals, but must not treat those as observed circuits.

O2's bounded AI proposal and confidence lane runs in parallel as a narrow support layer. It cannot replace deterministic geometry, registration, code checks or the O4 branch guard. The merged #302/#303 schedule work is reusable input evidence; #304 remains an unaccepted draft branch.

### Wave 2: complete canonical building and electrical design

After raw geometry and object registration are reliable, finish #72's observed circuit resolution and keep it separate from designed circuits. Build #228's per-run wiring method, bundle, cable/raceway, fitting, support and code decisions on the canonical router and explicit physical objects already present in main. #229 supplies the editable, versioned code/company/job rules required to make those decisions reproducible and reviewable.

Framing (#240), existing/demo scope (#231), and multi-source evidence (#239) can be developed as separate contract-safe lanes. Site/trench (#230), utility/service scope (#232), and low-voltage/security/fire (#236) can also be decomposed into independent issue-specific work once the relevant geometry, rule data and source evidence exist. Other trades are represented only when the plans actually draw them.

### Wave 3: downstream estimating, paperwork, viewer and change lifecycle

Once systems and quantities are reliable, generate #233's calculation and permit artifacts, #234's labor inputs, #237's system/trade views, and #235's priced change-order deltas. The canonical revision-diff foundation in #274 already reports comparable model and quantity changes, but it does not price or integrate them into OfficeAdmin. #238 adds field changes and as-built outputs on top of stable identities, multi-input evidence and revision tracking.

The exporter side of #88 is implemented in #269. #270 still needs the OfficeAdmin element panel and a visible display-thickness setting; an export spike is not a live viewer integration. O6 is building the bounded review bundle that consumes #241 evidence and #88/#270 display metadata. It is a read-only engine prerequisite; the OfficeAdmin correction panel and live integration remain later consumer work.

### Wave 4: independent end-to-end job acceptance

Only the complete run can close the north-star issue #227. The same reusable engine must accept representative residential, commercial, tenant-improvement and architectural-only inputs, including sets with and without electrical source evidence. No hand-selected pages or hidden manual geometry may seed the answer. For each job, compare the imported and designed model with a separate human-reviewed reference, record unresolved items and reasons, and follow accepted changes through routes, materials, drawings and exports.

An implementer does not certify their own gate. Public CI stays synthetic and deterministic. Real-job evaluation is run in the authorized private environment, and only public-safe aggregate evidence is brought back to this repository. A measured result must name its input class, sample size, reference method, exclusions and confidence; do not infer a broad accuracy rate from one case.

## Gaps that need explicit product decisions

These are real boundary gaps surfaced by the open issues. They receive no new issue numbers here.

- Production review/correction UI and live OfficeAdmin integration span a separate product repository. #229, #241 and #270 define parts of the contract, but no engine-only PR can claim those screens are live.
- Private, independent real-job regression remains separate from public CI. #42, #224, #259 and #227 require real-input evidence; the public fixture policy forbids placing customer plans, extracted text or private results in this repository.
- Complete multi-trade clash coordination is not implied by #240. Its current scope is framing plus other trades only when drawn; broader trade modeling needs a separate decision if that scope changes.
- The generic IFC input lane currently rejects untrusted generic IFC semantics rather than guessing. #239 owns broader input support; if its existing acceptance cannot contain a needed IFC subtype, record the gap before changing the contract.
- Routing and quantity foundations do not yet enforce electrical compatibility when routes are consolidated, and explicit hardware inventory does not prove support spacing, loading or fastener suitability. Add only modeled or explicitly selected items; do not add generic hardware allowances.
- A universally unattended run is an outcome, not a reason to conceal uncertainty. Until each input and rule class clears the real-job gates, keep review and correction available; do not advertise a no-human workflow based only on synthetic success.

## End-to-end acceptance report

For every real-job acceptance, keep these statements separate:

1. **Implemented:** name the code paths present on the tested commit.
2. **Merged:** name the PRs and exact main commit.
3. **Synthetic validation:** state fixtures and exact results.
4. **Real-data validation:** state the authorized input class, held-out reference method, sample size, exclusions, per-class outcome and independent reviewer. Keep confidential evidence private.
5. **Integrated/live:** identify the OfficeAdmin build or released flow that consumed the output and how it was verified.

The evaluator must run raw plan inputs through the normal path; expected answers stay separate from input. Report pages/sheets selected by deterministic classification, detected and unresolved entities by type, registration residuals, source-observed versus designed circuit counts, confidence/reason distributions, downstream route/quantity/drawing/export checks and deterministic rerun identity. Cross-check counts and material quantities against a human reference without feeding that reference into recognition or routing. Every code-bound calculation has a cited input edition and independent engineering review. Changes and corrections must replay through dependent artifacts without losing the original evidence.

A gate passes only when its criteria are written before the run, the output is independently reviewed, and the relevant issue’s closure evidence is linked. Until then, keep the issue open even if its child implementation is merged or CI is green.
